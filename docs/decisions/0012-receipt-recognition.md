# 0012 — Розпізнавання квитанцій: monobank, без криптоперевірки підпису

- Статус: **прийнято**
- Дата: 2026-11-08
- Автор: Олег
- Зачіпає: SPEC FR-PAY-3; `adapters/receipts/`; `payments.bank_reference`, `parsed`, `dispute_deadline`

## Контекст

M5, частина 2: квитанцію орендаря треба звірити з договором і, якщо все збіглося, зарахувати без участі власника (FR-PAY-3). Ми розібрали справжні PDF-квитанції monobank (локально, у git їх немає):

- файл з розширенням `.pdf` — насправді **контейнер CMS (PKCS#7, DER)**, усередині — PDF від Apache FOP. Контейнер підписаний КЕП АТ «Універсал Банк» (сертифікат від КНЕДП «Дія» або КНЕДП monobank). Час підпису — момент вивантаження квитанції, не операції;
- алгоритми — ДСТУ 4145 (підпис) і ДСТУ 7564 «Купина» (хеш);
- текст справжній (не картинка): номер квитанції `XXXX-XXXX-XXXX-XXXX`, сума, комісія, дата й час операції (Київ), призначення, **повний номер картки одержувача** й ім'я з ініціалом прізвища, дані відправника (IBAN, маска картки, ПІБ).

Посилання `check.monobank.ua/p/…` — сторінка банку; ходити туди автоматично — це скрейпінг стороннього сайту (правило 8 CLAUDE.md), тож працюємо лише з файлом.

## Рішення

1. **Адаптер `adapters/receipts/`** за `Protocol` `ReceiptReader`: `open()` дістає PDF (сам або з контейнера CMS) і дані підписувача; `parse()` витягує поля для відомого банку. Перший банк — monobank; ПриватБанк — коли буде зразок квитанції.
2. **Звірка — у домені** (`domain/payments.py`): сума ≥ залишку до сплати; одержувач — картка з договору (повний номер — точний збіг; замаскований — видимі цифри **і** ім'я) або IBAN; дата операції — не раніше ніж за 31 день до дати оплати й не в майбутньому; контейнер підписав саме банк. Номер квитанції (`bank_reference`) і SHA-256 файлу — унікальні, повтор відхиляється.
3. **Усе збіглося** → `auto_accepted`, `dispute_deadline` = зараз + вікно оскарження з умов оренди (типово 3 дні). Власник отримує сповіщення й може натиснути «Не отримав» → `disputed`. Після вікна воркер (`confirm_auto_payments`, щогодини) ставить `confirmed`. **Є розбіжність / фото / невідомий банк** → `pending_landlord`, обидві сторони бачать `mismatches`.
4. **Сума береться з квитанції**, а не з форми.
5. **Що зберігаємо** (правило 7): оригінальний файл (як доказ, у сховищі); у `payments.parsed` — банк, номер, суму, комісію, час, **маску** картки/IBAN одержувача, ім'я одержувача, ознаку підпису. Даних відправника й повного номера картки в БД немає. Власнику показуємо PDF зсередини контейнера.
6. **Підпис банку криптографічно не перевіряємо.** Для ДСТУ 4145 і «Купини» немає надійної бібліотеки для Python: знайдений `dstu-core` — pre-1.0, без аудиту, один анонімний автор, більшість версій відкликано; для публічного репозиторію це ризик ланцюга постачання. Писати криптографію з пам'яті не будемо.

## Наслідки

- **Ризик:** хто знає формат, може підробити PDF і загорнути його в будь-який контейнер із сертифікатом банку (той самий сертифікат є в кожній справжній квитанції). Захист зараз: збіг картки власника, унікальний номер квитанції, вікно оскарження й сповіщення власнику — гроші він бачить у своєму банку. Для бети прийнятно.
- **Пізніше:** перевірка підпису й хешу через EUSign (ІІТ) або сервіс ЦЗО — разом із підписами договорів (SPEC, «Відкриті питання», п. 2). Тоді `bank_signed` означатиме криптографічно перевірений підпис.
- Формат квитанції банк може змінити — тоді `parse()` поверне `None`, і квитанція піде власнику вручну (безпечний відкат). Тести — на вигаданих квитанціях тієї ж структури (`tests/receipt_fixtures.py`).
- Банка monobank: одержувача з квитанції не звірити з посиланням на банку — завжди вручну.
